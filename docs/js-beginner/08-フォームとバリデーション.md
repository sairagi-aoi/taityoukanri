# 第8章 フォームとバリデーション

## この章のゴール

- 入力チェック (バリデーション) がなぜ必要かを説明できる
- `validate()` の設計 ―「検査して、正しければデータを返す」を理解する
- 正規表現の基本が読める
- ユーザーに親切なエラー表示の作り方が分かる

---

## 8-1. なぜ入力チェックが必要か

ユーザーは、開発者が想定しない入力をします。悪意がなくても、です。

- 睡眠時間に `-5` と入れる (マイナス)
- 睡眠時間に `100` と入れる (1日は24時間)
- 睡眠時間に `７` と入れる (全角)
- プルダウンを選ばずに保存を押す
- 日付を消して空欄にする

これらをそのまま保存すると、**壊れたデータが `localStorage` に入り込みます**。
壊れたデータは、あとでグラフ描画や Excel 書き出しで予期しないエラーを引き起こします。

だから **「入口で止める」** のがバリデーションです。

### HTML だけでもある程度は防げる

`index.html` を見てください。

```html
<input type="number" id="sleep-hours" name="sleepHours"
       inputmode="decimal" min="0" max="24" step="0.5"
       placeholder="例: 7" required>
```

| 属性 | 効果 |
| --- | --- |
| `type="number"` | 数値用の入力欄になる (スマホで数字キーボードが出る) |
| `min="0"` `max="24"` | 範囲の指定 |
| `step="0.5"` | 0.5刻み |
| `required` | 必須 |
| `inputmode="decimal"` | スマホで小数点付きのキーボードを出す |

**HTML で書けることは HTML で書く。** これが第一原則です。
JavaScript を1行も書かずにスマホでの入力体験が良くなるのですから、使わない手はありません。

### それでも JavaScript のチェックが要る理由

`<form>` に `novalidate` が付いているのに気づきましたか？

```html
<form id="entry-form" novalidate>
```

`novalidate` は「ブラウザ標準のエラー表示を使わない」という指定です。なぜでしょう。

1. **ブラウザ標準のエラー表示はカスタマイズできない** (文言も見た目もブラウザ任せ)
2. **1つずつしか表示されない** (5項目未入力でも、1個目しか教えてくれない)
3. **開発者ツールから属性を消せる** ので、防御としては信用できない

このアプリは自前でチェックして、**未入力の項目をまとめて日本語で表示** しています。
そのほうが親切だからです。

> **重要**: 本格的な Web サービスでは、サーバー側でも必ず検証します。
> ブラウザ側のチェックは「親切のため」であって「安全のため」ではありません。
> このアプリはサーバーを持たない (データはユーザー自身のブラウザにしかない) ので、
> ブラウザ側の検証だけで完結しています。

## 8-2. `validate()` ― 検査と組み立てを兼ねる関数

```js
function validate() {
  clearInvalid();                        // ① 前回のエラー表示をリセット
  const missing = [];                    // ② 問題のある項目を集める配列

  if (!DATE_RE.test(dateInput.value)) {  // ③ 日付
    missing.push("日付");
    setFieldInvalid(dateInput, true);
  }

  for (const field of SCORE_FIELDS) {    // ④ 5つのプルダウン
    const select = $(SELECT_IDS[field]);
    if (select.value === "" || !isValidSelectValue(field, select.value)) {
      missing.push(FIELD_LABELS[field]);
      setFieldInvalid(select, true);
    }
  }

  const hoursRaw = sleepHoursInput.value.trim();   // ⑤ 睡眠時間
  const hours = parseSleepHours(hoursRaw);
  if (hours === null) {
    missing.push("睡眠時間 (0〜24)");
    setFieldInvalid(sleepHoursInput, true);
  }

  if (missing.length) {                  // ⑥ 1つでも問題があれば
    showError(`未入力または不正な項目があります: ${missing.join("、")}`);
    const first = form.querySelector(".field.invalid select, .field.invalid input, .field.invalid textarea");
    if (first) first.focus();
    return null;                         //    null を返して終了
  }

  hideError();
  return {                               // ⑦ 全部正しければ、記録オブジェクトを組み立てて返す
    date: dateInput.value,
    condition: Number($("condition").value),
    mental: Number($("mental").value),
    appetite: Number($("appetite").value),
    motivation: Number($("motivation").value),
    sleepHours: hours,
    sleepQuality: Number($("sleep-quality").value),
    memo: memoInput.value.trim().slice(0, MEMO_MAX),
    updatedAt: new Date().toISOString(),
  };
}
```

### この設計の優れている点

**「検査に成功したら、そのまま使えるデータを返す」** という形になっています。

```js
const entry = validate();
if (!entry) return;          // null なら何もしない
entries[entry.date] = entry; // すぐ使える
```

呼ぶ側は「`null` かどうか」だけ見ればよく、値の取り出しも変換も済んでいます。
もし `validate()` が `true` / `false` だけ返す設計だったら、
呼ぶ側でもう一度フォームから値を取って変換する必要がありました。

`scoreValue` や `parseSleepHours` も同じパターンです。
**「正しければ変換済みの値、不正なら `null`」** という統一された約束事が、
コード全体で一貫しています。

### エラーをまとめて表示する

```js
const missing = [];
// ... 問題があるたびに missing.push(...)
showError(`未入力または不正な項目があります: ${missing.join("、")}`);
```

`join("、")` は配列を「、」でつないだ文字列にします。

```js
["体調", "食欲", "睡眠時間 (0〜24)"].join("、")
// "体調、食欲、睡眠時間 (0〜24)"
```

結果として「未入力または不正な項目があります: 体調、食欲、睡眠時間 (0〜24)」となります。
**一度にすべて教える** ので、ユーザーは1回で直せます。

1つずつ教える設計だと、直して → 保存 → また怒られる、を5回繰り返させることになります。

### 最初のエラー箇所にフォーカスする

```js
const first = form.querySelector(".field.invalid select, ...");
if (first) first.focus();
```

エラーになった最初の入力欄にカーソルを移します。
入力欄が多いフォームでは「どこを直せばいいのか」を探す手間が省けて、地味に効きます。

## 8-3. 正規表現の基本

このアプリには2つの正規表現が出てきます。

```js
const DATE_RE = /^\d{4}-\d{2}-\d{2}$/;          // 日付の形式
if (!/^\d+(\.\d+)?$/.test(raw)) return null;    // 数値の形式
```

正規表現は「文字列のパターン」を表す小さな言語です。`/` と `/` で囲んで書きます。

### 基本の記号

| 記号 | 意味 | 例 |
| --- | --- | --- |
| `^` | 先頭 | `/^abc/` は "abc" で始まる |
| `$` | 末尾 | `/abc$/` は "abc" で終わる |
| `\d` | 数字1文字 (0〜9) | |
| `.` | 任意の1文字 | |
| `+` | 直前が1回以上 | `\d+` は "1", "42", "999" |
| `*` | 直前が0回以上 | |
| `?` | 直前が0回か1回 (省略可) | |
| `{n}` | 直前がちょうど n 回 | `\d{4}` は "2026" |
| `( )` | グループにまとめる | |

### `DATE_RE` を読む

```
/^\d{4}-\d{2}-\d{2}$/
 ^        先頭から
 \d{4}    数字4個      → 2026
 -        ハイフン
 \d{2}    数字2個      → 09
 -        ハイフン
 \d{2}    数字2個      → 16
 $        末尾まで
```

つまり `"2026-09-16"` のような形だけを通します。

```js
DATE_RE.test("2026-09-16")     // true
DATE_RE.test("2026-9-16")      // false  ← 桁が足りない
DATE_RE.test("x2026-09-16")    // false  ← ^ があるので先頭に余計な文字は不可
DATE_RE.test("2026-99-99")     // true   ← 形式は合っている (日付として妥当かは見ていない)
```

最後に注意してください。**形式のチェックであって、日付として存在するかのチェックではありません。**
このアプリでは `<input type="date">` が実在しない日付を入れさせないので、これで十分という判断です。

### 睡眠時間の正規表現

```
/^\d+(\.\d+)?$/
 ^        先頭から
 \d+      数字が1個以上     → "7", "12"
 ( )?     カッコの中が省略可能
   \.     ピリオド (「.」は任意の1文字の意味なので \ でエスケープ)
   \d+    数字が1個以上
 $        末尾まで
```

```js
/^\d+(\.\d+)?$/.test("7")       // true
/^\d+(\.\d+)?$/.test("7.5")     // true
/^\d+(\.\d+)?$/.test("-5")      // false ← マイナスは書かれていない
/^\d+(\.\d+)?$/.test("7.")      // false ← 「.」の後には数字が必要
/^\d+(\.\d+)?$/.test("7時間")   // false ← $ があるので余計な文字は不可
/^\d+(\.\d+)?$/.test("７")      // false ← 全角数字は \d に含まれない
```

### なぜ `Number()` だけで済ませないのか

`Number("-5")` は `-5` を返すので、これだけでは負の値を弾けません。
実際 `parseSleepHours` は正規表現・`Number.isFinite`・範囲チェックの **3重** になっています。

```js
function parseSleepHours(v) {
  if (v === null || v === undefined || v === "") return null;
  const raw = String(v).trim();
  if (!/^\d+(\.\d+)?$/.test(raw)) return null;          // 形式
  const hours = Number(raw);
  if (!Number.isFinite(hours) || hours < 0 || hours > 24) return null;  // 値
  return Math.round(hours * 100) / 100;
}
```

また `Number` は少し変わった挙動をします。

```js
Number("")          // 0      ← 空文字が 0 になってしまう！
Number("  ")        // 0
Number("0x10")      // 16     ← 16進数として解釈される
Number("1e3")       // 1000   ← 指数表記も通る
Number(null)        // 0
Number(undefined)   // NaN
```

`Number("")` が `0` になるのは危険です。「未入力」が「睡眠0時間」として保存されてしまいます。
だから **先に正規表現で形式を確かめてから `Number` に渡す** 順序になっているのです。

## 8-4. エラー表示の仕組み

エラー表示は3段階の構成です。

### ① メッセージ全体

```js
function showError(msg) {
  formError.textContent = msg;
  formError.hidden = false;
}

function hideError() {
  formError.hidden = true;
  formError.textContent = "";
}
```

対応する HTML はこれです。

```html
<p id="form-error" class="form-error" role="alert" hidden></p>
```

`role="alert"` により、スクリーンリーダーが **中身が入った瞬間に読み上げます**。

### ② 個別の入力欄をマークする

```js
function setFieldInvalid(el, invalid) {
  const field = el.closest(".field");
  if (!field) return;
  field.classList.toggle("invalid", invalid);
  const control = field.querySelector("select, input, textarea");
  if (control) control.setAttribute("aria-invalid", invalid ? "true" : "false");
}
```

見た目のための `invalid` クラスと、支援技術のための `aria-invalid` 属性を **両方** 付けています。
目で見える人にも、見えない人にも、同じ情報が届きます。

### ③ 入力し直したらエラーを消す

```js
select.addEventListener("change", () => {
  updateSelectStyle(select);
  setFieldInvalid(select, false);   // ← 選び直したら赤枠を消す
});

sleepHoursInput.addEventListener("input", () => {
  setFieldInvalid(sleepHoursInput, false);
});
```

**直し始めたら、すぐエラー表示が消える。** これがあるかないかで、印象がまったく違います。

### 説明の紐付け

初期化の最後に、こんな1行があります。

```js
for (const field of form.querySelectorAll(".field select, .field input, .field textarea")) {
  field.setAttribute("aria-describedby", "form-error");
}
```

「この入力欄の説明は `form-error` にあるよ」と、すべての入力欄に教えています。
スクリーンリーダーは入力欄にフォーカスしたとき、エラーメッセージも一緒に読んでくれます。

## 8-5. フォームの状態を管理する

このアプリのフォームには「新規入力」と「編集」の2つのモードがあります。
しかし **モードを表す変数はありません**。代わりにこう書かれています。

```js
function syncEditState() {
  const exists = Boolean(entries[dateInput.value]);   // ← 日付から判定する
  editBadge.hidden = !exists;
  saveBtn.textContent = exists ? "上書き保存する" : "保存する";
  for (const tr of tbody.querySelectorAll("tr")) {
    tr.classList.toggle("is-editing", tr.dataset.date === dateInput.value);
  }
  updateHeaderStatus();
}
```

**「今フォームに入っている日付の記録が既に存在するか」だけで、すべてが決まります。**

モード変数を持つと、「モードの更新を忘れる」というバグが必ず起きます。
データから毎回計算すれば、**ズレようがありません**。

これは「Single Source of Truth (信頼できる唯一の情報源)」という考え方で、
モダンなフロントエンド開発の中心的な原則です。このアプリはライブラリを使わずにそれを実践しています。

### フォームのリセット

```js
function resetForm(keepDate) {
  const date = keepDate ? dateInput.value : todayString();
  form.reset();            // ブラウザ標準のリセット
  dateInput.value = date;  // 日付だけは復元
  lastDateValue = date;
  for (const field of SCORE_FIELDS) {
    const select = $(SELECT_IDS[field]);
    select.value = "";
    updateSelectStyle(select);
  }
  clearInvalid();
  hideError();
  syncEditState();
  setFormBaseline();
}
```

`keepDate` という引数で「日付は残すか」を切り替えています。

- 削除後・クリア後 → `resetForm(true)` (日付はそのまま、中身だけ消す)
- 日付を変えたとき → `resetForm(true)`

`form.reset()` だけでは `<select>` の状態やクラスが元に戻らないので、
手動で `select.value = ""` と `updateSelectStyle` を呼び直しています。

## まとめ

- バリデーションは **壊れたデータを入口で止める** ためにある
- HTML の `type` `min` `max` `required` でできることは HTML でやる。ただしそれだけに頼らない
- `validate()` は **「正しければ使えるデータ、不正なら `null`」** を返す。呼ぶ側が簡単になる
- エラーは **まとめて、日本語で、直すべき場所にフォーカスして** 伝える
- 正規表現は `^` と `$` で両端を固定する。`Number("")` が `0` になる罠を先に潰す
- 見た目 (`invalid` クラス) と支援技術 (`aria-invalid`) の両方に対応する
- モードを変数で持たず、**データから毎回計算する** とズレが起きない

次章は、データをブラウザに保存する `localStorage` です。
