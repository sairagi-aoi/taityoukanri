# 第11章 エラー処理と堅牢なコード

## この章のゴール

- `try...catch` の使い方と、使うべき場所が分かる
- 「壊れたデータ」「失敗する操作」への備え方を説明できる
- `app.js` に仕込まれた防御を一通り見つけられる
- 良いコードとは何かを、実例を通して言語化できる

---

## 11-1. エラーは「起きるもの」

初学者は「バグがなければエラーは起きない」と考えがちですが、違います。
**正しく書いても起きるエラー** があります。

| 原因 | 例 |
| --- | --- |
| ユーザーの入力 | 想定外の値、空欄 |
| 環境の制約 | localStorage が使えない、容量オーバー |
| データの破損 | 手で書き換えられた、古い形式のまま |
| ブラウザの違い | 対応していない機能 |

だからプロのコードには、**エラーが起きる前提の備え** が必ず入っています。
`app.js` はこの点でとても良い教材です。

---

## 11-2. `try...catch`

```js
try {
  // エラーが起きるかもしれない処理
} catch (e) {
  // エラーが起きたときの処理。e にエラー情報が入る
}
```

`try` の中でエラーが起きると、**その場で `catch` に飛びます**。
プログラムは止まらず、続きを実行できます。

### 例1: 保存の失敗を吸収する

```js
function persistEntries() {
  try {
    saveEntries(entries);
    return true;
  } catch (e) {
    return false;
  }
}
```

`localStorage.setItem` は容量オーバーなどで例外を投げます。
それを捕まえて **`true` / `false` という扱いやすい形に変換** しています。

呼ぶ側はエラーのことを知らずに済みます。

```js
if (!persistEntries()) {
  // 失敗時の処理
}
```

**「例外を、扱いやすい戻り値に変える」** のは、よく使われる設計パターンです。

### 例2: 読み込みの失敗を吸収する

```js
function loadEntriesRaw() {
  try {
    const raw = localStorage.getItem(STORAGE_KEY);
    if (!raw) return {};
    const parsed = JSON.parse(raw);
    return parsed && typeof parsed === "object" && !Array.isArray(parsed) ? parsed : {};
  } catch (e) {
    console.warn("保存データの読み込みに失敗しました", e);
    return {};
  }
}
```

ここでは `console.warn` でログを残しています。
**握りつぶすのではなく、開発者には伝える** という姿勢です。
ユーザーには見せず、Console には残す。バランスの取れた判断です。

### 例3: 何もしない `catch`

```js
try {
  if (localStorage.getItem(STORAGE_KEY) !== JSON.stringify(entries)) {
    persistEntries();
  }
} catch (_) {
  /* 読み取り不可環境では同期をスキップ */
}
```

ここでは意図的に何もしていません。ただし **コメントで理由を書いています**。

> **原則**: エラーを無視するなら、**なぜ無視してよいのかをコメントに書く**。
> コメントのない空の `catch` は、単なるバグの隠蔽です。

`catch (_)` の `_` は「使わない」という意思表示の慣習です。

## 11-3. `try...catch` を使わない備え

例外を捕まえるより、**そもそもエラーにしない** ほうが良い場合があります。

### `null` チェック

```js
const first = form.querySelector(".field.invalid select, ...");
if (first) first.focus();

const field = el.closest(".field");
if (!field) return;

const btn = ev.target.closest("button[data-action]");
if (!btn) return;

if (!trendsWrap || !trendsSvg) return;
if (!monthFilterEl) return;
if (!appToast) return;
```

DOM の取得は失敗しうるので (id のスペルミス、HTML の変更)、
**使う前に必ず存在を確かめる**。これが `app.js` の一貫した姿勢です。

### 既定値

```js
memoInput.value = e.memo || "";
(e.memo || "").slice(0, MEMO_MAX)
const sheetName = (opts.sheetName || "Sheet1").slice(0, 31);
if (!rows.length) rows = [[""]];
```

`undefined` が来ても動くようにしています (第5章の `||` の活用)。

### 範囲の制限

```js
memo.slice(0, MEMO_MAX)                 // 500文字まで
keys.slice(0, MAX_ENTRIES)              // 5000件まで
sheetName.slice(0, 31)                  // Excel の制限
```

「異常に大きなデータが来ても壊れない」ようにしています。

### 型と値の検証

```js
function scoreValue(v) {
  const n = Number(v);
  if (!Number.isInteger(n) || n < 1 || n > 5) return null;
  return n;
}
```

`Number.isInteger` は `NaN` も小数も弾いてくれます。

```js
Number.isInteger(3)      // true
Number.isInteger(3.5)    // false
Number.isInteger(NaN)    // false
Number.isInteger("3")    // false  ← 文字列も弾く
```

`Number.isFinite` は `Infinity` も弾きます。

```js
Number.isFinite(1/0)     // false  (Infinity)
Number.isFinite(NaN)     // false
Number.isFinite(7.5)     // true
```

こうした「型を確かめる関数」を知っていると、検証が簡潔に書けます。

## 11-4. データの境界を守る

良い設計には **「境界」** があります。
外の世界から入ってくるデータは、境界で必ず検証されます。

```
┌─────────────────── アプリの内側 ───────────────────┐
│                                                     │
│  entries (常に正しい形をしていると保証されている)   │
│                                                     │
└──▲──────────────────────────────────────▲──────────┘
   │ normalizeStore / normalizeEntry      │ validate()
   │                                       │
localStorage (信用できない)          フォーム入力 (信用できない)
```

境界は2つだけです。

| 入口 | 検証する関数 |
| --- | --- |
| localStorage からの読み込み | `normalizeStore` → `normalizeEntry` |
| フォームからの入力 | `validate` |

**この2つを通ったデータだけが `entries` に入る。**
だから `renderList` や `buildExportRows` は、値が正しいことを前提に書けます。

### それでも二重に守る

ただし `app.js` は、内側でももう一度チェックしています。

```js
function appendDot(parent, level) {
  const n = scoreValue(level);
  if (n === null) return;    // ← ここでも検証
  // ...
}

const sc = scoreValue(entries[date][s.key]);
if (sc === null) return null;   // ← グラフ描画でも検証
```

「検証済みのはずなのに、なぜまた？」と思うかもしれません。理由は2つあります。

1. 将来コードが変わって、検証を通らない経路ができるかもしれない
2. チェックのコストが小さく、失敗時の被害が大きい (画面が壊れる)

**安いチェックは重ねてよい。** これは実務でよく使われる考え方です。

## 11-5. 失敗しても壊れない ― 巻き戻し

第9章で見た巻き戻しは、エラー処理の重要な形です。

```js
const backup = { ...entries };     // ① 退避
entries = {};                       // ② 変更
if (!persistEntries()) {            // ③ 永続化を試す
  entries = backup;                 // ④ 失敗したら戻す
  flashSaveError();
  return;
}
renderList();                       // ⑤ 成功したときだけ画面を更新
```

ポイントは **⑤の位置** です。
`renderList()` が `if` の後にあるので、**保存が成功したときしか画面が更新されません**。

もし `renderList()` を先に呼んでいたら、「画面では消えているのに、リロードすると復活する」という
不気味な状態になります。

> **原則**: 画面の更新は、データの確定後に行う。
> 「見た目だけ先に変える」と、失敗時に嘘をつくことになります。

## 11-6. ユーザーへの伝え方

エラーが起きたとき、ユーザーに何を伝えるかも設計です。

```js
function flashSaveError() {
  flash("保存に失敗しました。ブラウザの保存領域が使えない可能性があります。", true);
}
```

このメッセージは良い例です。

- **何が起きたか**: 保存に失敗した
- **なぜかもしれないか**: 保存領域が使えない
- **専門用語を避けている**: 「QuotaExceededError」とは言わない

悪い例と比べてみてください。

```
✗ "Error"
✗ "QuotaExceededError: Failed to execute 'setItem' on 'Storage'"
✗ "エラーが発生しました"
✓ "保存に失敗しました。ブラウザの保存領域が使えない可能性があります。"
```

### 深刻度で伝え方を変える

```js
flash("書き出す記録がありません。", true);       // 一時的な通知 (4秒で消える)
showError("保存に失敗しました。...");            // フォーム内に留まる表示
console.warn("保存データの読み込みに失敗しました", e);   // 開発者だけに
```

- **一時的な通知 (toast)** … 軽い情報。放っておいても消える
- **フォーム内のエラー** … 直すまで消えない。行動が必要
- **Console のログ** … ユーザーには見せないが、開発者が調べられる

3つを使い分けているのが、このアプリの丁寧なところです。

## 11-7. `app.js` の防御一覧

実際にどれだけ備えがあるか、まとめて見てみましょう。

| 場所 | 備えていること |
| --- | --- |
| `loadEntriesRaw` | データが無い / JSON が壊れている / 配列だった |
| `normalizeStore` | キーが日付形式でない / 件数が多すぎる |
| `normalizeEntry` | 項目が欠けている / 型が違う / オブジェクトでない |
| `scoreValue` | 1〜5 の整数でない |
| `parseSleepHours` | 空 / 数字でない / 範囲外 / 小数の誤差 |
| `validate` | 未入力 / 不正な選択肢 / メモが長すぎる |
| `persistEntries` | localStorage の例外 |
| `saveEntries` の呼び出し側 | 保存失敗時の巻き戻し |
| `setFieldInvalid` | `.field` が見つからない |
| イベントハンドラ | ボタン以外のクリック / `dataset` の改竄 |
| `renderList` | `entries[date]` が無い (`if (!e) continue`) |
| `renderTrendsChart` | 要素が無い / データが2件未満 / 点が2個未満 |
| `exportExcel` | 記録が0件 |
| `flash` | toast 要素が無い |
| `labelOf` | 該当するラベルが無い |

**約25KB のコードのうち、かなりの割合が「異常系」に使われています。**
これが実務のコードの姿です。「正常に動くコード」を書くのは半分で、
残りの半分は「異常でも壊れないコード」を書く仕事です。

## 11-8. 良いコードの条件 ― このアプリから学べること

`app.js` を読んできて見えてくる原則をまとめます。

### 1. 名前で説明する

```js
const MEMO_MAX = 500;               // 500 とだけ書かない
function computeStreak() { ... }    // 名前だけで何をするか分かる
```

### 2. 1つの関数は1つの仕事

小さい関数を組み合わせて大きな仕事をする。`computeStreak` が `todayString` と `addDays` を呼ぶように。

### 3. データ構造を先に考える

`entries` を日付キーのオブジェクトにしたことで、保存も削除も1行になった (第3章)。

### 4. 状態を持たず、データから計算する

「編集モードかどうか」の変数を持たず、`Boolean(entries[dateInput.value])` で毎回判定する (第8章)。

### 5. 外から来たデータを信用しない

localStorage も、フォーム入力も、`dataset` も、必ず検証してから使う。

### 6. 失敗したら元に戻す

変更 → 永続化 → 失敗なら巻き戻し。画面の更新は成功後。

### 7. 見た目は CSS に任せる

JavaScript はクラスを付け外しするだけ。色やサイズは知らない (第6章)。

### 8. 標準の仕組みに乗る

`<form>` の `submit`、`<input type="date">`、`Date` の日付計算。
自前で書かずに済むものは書かない。

### 9. ユーザーに配慮する

まとめてエラーを出す、変更がなければ確認しない、直し始めたら赤枠を消す、
`aria-label` を付ける。**技術は人のためにある。**

### 10. できないことを認め、逃げ道を用意する

localStorage は端末間で共有できない → だから Excel 書き出しがある。

## まとめ

- エラーは「バグ」ではなく「起きるもの」。備えるのが仕事
- `try...catch` で例外を捕まえ、**扱いやすい戻り値に変換する**
- エラーを無視するなら、**理由をコメントに書く**
- `null` チェック・既定値・範囲制限・型検証で、そもそもエラーにしない
- **境界 (localStorage とフォーム) で検証し、内側は安全にする**
- 失敗したら巻き戻す。**画面の更新はデータ確定後**
- エラーメッセージは「何が起きたか」「どうすればよいか」を平易な言葉で

次章は、このアプリで使われている一歩進んだ技術を見ていきます。
