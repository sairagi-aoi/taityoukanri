# 第14章 演習の解答例

**解答は1つではありません。** ここに示すのは「こう書ける」という一例です。
自分の書いたコードのほうが読みやすいと思ったら、それが正解かもしれません。

## 問1. ラベルを変える

`app.js` の `OPTIONS` を1か所だけ直します。

```js
const OPTIONS = {
  condition: [
    { value: 5, label: "とても良い" },
    { value: 4, label: "良い" },
    { value: 3, label: "まあまあ" },   // ← ここだけ
    { value: 2, label: "やや悪い" },
    { value: 1, label: "悪い" },
  ],
  // mental などは変更しない
};
```

### なぜ1か所で済むのか

第1章と第3章で見たとおり、**ラベルが登場するすべての場所が `OPTIONS` を参照している** からです。

| 場所 | 参照の仕方 |
| --- | --- |
| プルダウンの選択肢 | `populateSelects()` が `OPTIONS[field]` をループ |
| 一覧の表示 | `labelOf("condition", e.condition)` が `OPTIONS[field].find(...)` |
| Excel 書き出し | 同じく `labelOf` |

**データを1か所に集める** ことの威力です。
もし HTML に直接 `<option>` を書いていたら、3か所を直す必要がありました。

> **なお**: 既に保存済みのデータには影響しません。保存されているのは数値 (`3`) だけで、
> ラベルは表示のたびに引き直されるからです。これも良い設計です。

## 問2. メモの上限を変える

**2か所** 直します。

```js
// app.js
const MEMO_MAX = 200;
```

```html
<!-- index.html -->
<textarea id="memo" name="memo" rows="2" maxlength="200" placeholder="気になったことがあれば一言"></textarea>
```

### なぜ両方必要か

| | 役割 | これだけだと |
| --- | --- | --- |
| `maxlength="200"` | **入力できないようにする** (親切) | 開発者ツールで属性を消せば突破できる |
| `MEMO_MAX = 200` | **保存する前に切り詰める** (確実) | 201文字打ててしまい、保存時に黙って切られる |

両方あって初めて「打てないし、万一打てても切られる」となります。
第8章の「HTML でできることは HTML で。ただしそれだけに頼らない」の実践です。

`MEMO_MAX` は `validate()` と `normalizeEntry()` の両方で使われているので、
**保存経路でも読み込み経路でも** 200文字に制限されます。

## 問4. 平均スコアを表示する

### index.html

```html
<p class="header-meta">
  <span id="today-status" class="today-status is-pending">今日: 未記録</span>
  <span id="streak-info" class="streak-info">連続記録なし</span>
  <span id="avg-info" class="streak-info"></span>
</p>
```

### app.js

要素を取得します。

```js
const avgEl = $("avg-info");
```

平均を計算する関数を追加します (`computeStreak` の近くに)。

```js
/** 今月の体調スコアの平均。記録が無ければ null */
function monthlyAverage(field) {
  const ym = currentYearMonth();
  const scores = sortedDates()
    .filter((d) => d.startsWith(ym))
    .map((d) => scoreValue(entries[d][field]))
    .filter((s) => s !== null);
  if (!scores.length) return null;          // ← 0除算を防ぐ
  const sum = scores.reduce((acc, n) => acc + n, 0);
  return Math.round((sum / scores.length) * 10) / 10;
}
```

`updateHeaderStatus` に表示処理を追加します。

```js
function updateHeaderStatus() {
  if (!todayStatusEl || !streakEl) return;
  // ... 既存の処理はそのまま
  const streak = computeStreak();
  streakEl.textContent = streak > 0 ? `連続 ${streak} 日` : "連続記録なし";

  if (avgEl) {
    const avg = monthlyAverage("condition");
    avgEl.textContent = avg === null ? "" : `今月の体調平均 ${avg}`;
    avgEl.hidden = avg === null;
  }
}
```

### ポイント

**0件のときの処理が最重要** です。

```js
[].reduce((a, n) => a + n, 0) / 0   // NaN
```

`if (!scores.length) return null;` がないと、記録が1件もない月に `NaN` が表示されます。
第5章の「falsy」と第11章の「防御」がここで効きます。

`.filter((s) => s !== null)` も入れてあります。
`entries` は検証済みのはずですが、**安いチェックは重ねてよい** (第11章)。

`updateHeaderStatus()` の中に書いた理由は、この関数が
`syncEditState()` から呼ばれ、`syncEditState()` が `renderList()` から呼ばれるからです。
**データが変わるたびに自動で更新されます。** 呼び出しを自分で追加する必要はありません。

`Math.round(x * 10) / 10` は小数第1位に丸めるイディオムです。
`toFixed(1)` でもよいですが、`toFixed` は文字列を返し、`3.0` のように 0 も表示します。
どちらが好みかで選んでください。

## 問5. 睡眠時間もグラフに追加する

`series` の仕組みを拡張して、系列ごとに変換関数を持たせるのがきれいです。

```js
function renderTrendsChart() {
  // ... 座標系の準備は既存のまま

  function yPos(score) {
    return pad.t + ih - ((score - 1) / 4) * ih;
  }
  function ySleepPos(hours) {
    const clamped = Math.min(Math.max(hours, 0), 12);   // 0〜12 に収める
    return pad.t + ih - (clamped / 12) * ih;
  }
  function xPos(i) {
    return pad.l + (i / (all.length - 1)) * iw;
  }

  const series = [
    { key: "condition", stroke: "var(--level-5)", label: "体調", toY: yPos },
    { key: "mental", stroke: "var(--accent)", label: "メンタル", toY: yPos },
    { key: "sleepHours", stroke: "var(--level-2)", label: "睡眠時間", toY: ySleepPos, raw: true },
  ];

  // ... 目盛り線の描画は既存のまま

  for (const s of series) {
    const points = all
      .map((date, i) => {
        const v = s.raw
          ? parseSleepHours(entries[date][s.key])
          : scoreValue(entries[date][s.key]);
        if (v === null) return null;
        return `${xPos(i)},${s.toY(v)}`;
      })
      .filter(Boolean);
    if (points.length < 2) continue;

    const poly = document.createElementNS("http://www.w3.org/2000/svg", "polyline");
    poly.setAttribute("fill", "none");
    poly.setAttribute("stroke", s.stroke);
    poly.setAttribute("stroke-width", "2");
    poly.setAttribute("points", points.join(" "));
    trendsSvg.appendChild(poly);
  }

  const title = document.createElementNS("http://www.w3.org/2000/svg", "title");
  title.textContent = `直近${all.length}日の体調・メンタル・睡眠時間`;
  trendsSvg.appendChild(title);
}
```

### ポイント

- **スケールが違う値を同じグラフに描くのは、本来やってはいけません。**
  「体調3」と「睡眠7時間」を同じ高さに描くのは、見る人に誤解を与えます。
  実務なら **右側に第2の軸を描いて、目盛りを明示する** べきです
- `Math.min(Math.max(x, 0), 12)` は「0〜12の範囲に収める (clamp)」イディオムです。
  14時間寝た日があってもグラフが枠から飛び出しません
- `series` に `toY` という **関数を入れている** のがポイントです。
  第4章で学んだ「関数を値として扱える」性質の応用です
- 凡例 (どの色が何か) がないと読めません。余力があれば `<text>` 要素で追加してください

## 問7. CSV でも書き出せるようにする

### index.html

```html
<button type="button" class="btn btn-ghost btn-sm" id="export-btn">Excelで書き出し</button>
<button type="button" class="btn btn-ghost btn-sm" id="export-csv-btn">CSVで書き出し</button>
```

### app.js

ダウンロード処理が2か所に増えるので、**共通の関数に切り出します**。

```js
/** Blob をファイルとしてダウンロードさせる */
function downloadBlob(blob, filename) {
  const url = URL.createObjectURL(blob);
  const a = document.createElement("a");
  a.href = url;
  a.download = filename;
  document.body.appendChild(a);
  a.click();
  a.remove();
  setTimeout(() => URL.revokeObjectURL(url), 1000);
}
```

`exportExcel` もこれを使うように書き換えます。

```js
function exportExcel() {

  const rows = buildExportRows();

    sheetName: "体調記録",

```

CSV の処理を追加します。

```js
/** CSV の1セルをエスケープする */
function csvCell(v) {
  if (v === null || v === undefined) return "";
  const s = String(v);
  // カンマ・改行・ダブルクォートを含むなら、" で囲んで中の " を "" にする
  if (/[",\r\n]/.test(s)) {
    return `"${s.replace(/"/g, '""')}"`;
  }
  return s;
}

function exportCsv() {
  if (!Object.keys(entries).length) {
    flash("書き出す記録がありません。", true);
    return;
  }
  const rows = buildExportRows();
  const csv = rows.map((row) => row.map(csvCell).join(",")).join("\r\n");
  // 先頭の ﻿ は BOM。これがないと Excel で開いたとき文字化けする
  const blob = new Blob(["﻿" + csv], { type: "text/csv;charset=utf-8" });
  downloadBlob(blob, `体調記録_${todayString()}.csv`);
  flash(`${rows.length - 1}件をCSVファイルに書き出しました。`);
}

$("export-csv-btn").addEventListener("click", exportCsv);
```

### ポイント

#### エスケープが必須である理由

メモに `今日は、よく眠れた` と書かれていた場合:

```
2026-09-16,とても良い,5,...,今日は、よく眠れた     ← 全角の「、」なので実はセーフ
2026-09-16,とても良い,5,...,today was, good      ← 半角カンマだと列がずれる！
```

`csvCell` を通すと `"today was, good"` になり、正しく1つのセルとして扱われます。

メモに `"` が含まれる場合は、CSV の規格 (RFC 4180) により `""` と2つ重ねます。

```
彼は"元気"と言った   →   "彼は""元気""と言った"
```

#### BOM の話

BOM (Byte Order Mark) は `﻿` という目に見えない1文字です。
これがないと、日本語版 Excel は CSV を Shift_JIS だと思い込んで **文字化けします**。

Excel 以外のツール (Python の pandas など) では BOM が邪魔になることもあるので、
「Excel で開く前提なら付ける」と覚えておいてください。

#### 改行コード

`join("\r\n")` としています。CSV の規格では `\r\n` (CRLF) が正式です。
`\n` だけでも大抵のツールは読めますが、規格に従うほうが無難です。

#### 共通化の判断

`downloadBlob` を切り出したのは、同じ6行が2か所に現れるからです。
**同じコードが2回出てきたら関数にする** (第4章)。3回目が来る前に、です。

## 問8. タグ機能を追加する

### データ構造

各記録に `tags` を追加します。

```js
{

  condition: 5,
  // ...
  memo: "",
  tags: ["頭痛", "残業"],     // ← 追加
  updatedAt: "..."

```

### 定数を追加

```js
const TAG_MAX = 8;          // 1件あたりのタグ数の上限
const TAG_LEN_MAX = 20;     // タグ1個の文字数の上限
```

### index.html

```html
<div class="field">
  <label for="tags">タグ <span class="optional">(任意・カンマ区切り)</span></label>
  <input type="text" id="tags" name="tags" maxlength="200" placeholder="例: 頭痛, 残業">
</div>
```

### 正規化 (`normalizeEntry`)

**ここが一番重要です。既存データとの互換性を保ちます。**

```js
/** 任意の入力をタグ配列に正規化する */
function normalizeTags(raw) {
  if (!Array.isArray(raw)) return [];              // ← tags が無い既存データは [] になる
  const out = [];
  for (const t of raw) {
    if (typeof t !== "string") continue;
    const s = t.trim().slice(0, TAG_LEN_MAX);
    if (!s) continue;
    if (out.includes(s)) continue;                 // 重複を除く
    out.push(s);
    if (out.length >= TAG_MAX) break;              // 上限で打ち切る
  }
  return out;
}
```

`normalizeEntry` に組み込みます。

```js
return {
  date,
  ...scores,
  sleepHours,
  memo,
  tags: normalizeTags(raw.tags),   // ← 追加
  updatedAt,
};
```

**`return null` にしていない** ことに注目してください。
タグは任意の項目なので、不正でも記録ごと捨てる必要はありません。
空配列にして先に進みます。**必須項目と任意項目で扱いを変える** のが設計です。

### 入力のパース (`validate`)

```js
/** "頭痛, 残業" → ["頭痛", "残業"] */
function parseTagsInput(v) {
  return normalizeTags(String(v || "").split(",").map((s) => s.trim()));
}
```

`validate()` の返り値に追加します。

```js
return {
  date: dateInput.value,
  // ...
  memo: memoInput.value.trim().slice(0, MEMO_MAX),
  tags: parseTagsInput(tagsInput.value),   // ← 追加
```

`normalizeTags` を使い回しているので、**検証ルールが1か所にまとまっています**。
これが第11章で見た「境界での検証」の実践です。

### ポイント

- **既存データとの互換性が最大の論点** でした。`normalizeTags` が
  `Array.isArray` でないものを `[]` にするので、タグのない古い記録もそのまま読めます
- こういう変更を **マイグレーション (移行)** と呼びます。
  実務では、データ構造を変えるたびにこの考慮が必要になります
- `getFormSnapshot` への追加を忘れると、微妙なバグ (タグを編集したのに確認が出ない) になります。
  **状態を複数箇所で管理していると、こういう漏れが起きます。** 設計の難しさです

### index.html

### 書き出し

```js
function exportJson() {
  if (!Object.keys(entries).length) {
    flash("書き出す記録がありません。", true);
    return;
  }
  const text = JSON.stringify(entries, null, 2);
  const blob = new Blob([text], { type: "application/json" });
  downloadBlob(blob, `体調記録_backup_${todayString()}.json`);   // 問7 の関数を再利用
  flash(`${Object.keys(entries).length}件をJSONファイルに書き出しました。`);
}

$("export-json-btn").addEventListener("click", exportJson);
```

### 読み込み

```js
const importInput = $("import-json-input");

importInput.addEventListener("change", async (ev) => {
  const file = ev.target.files && ev.target.files[0];
  if (!file) return;

  let parsed;
  try {
    const text = await file.text();
    parsed = JSON.parse(text);
  } catch (e) {
    console.warn("インポートに失敗しました", e);
    flash("ファイルを読み込めませんでした。JSON形式か確認してください。", true);
    importInput.value = "";
    return;
  }

  if (!parsed || typeof parsed !== "object" || Array.isArray(parsed)) {
    flash("このファイルは体調記録のバックアップではないようです。", true);
    importInput.value = "";
    return;
  }

  // ★ 必ず正規化を通す。外から来たデータは信用しない (第11章)
  const incoming = normalizeStore(parsed);
  const incomingCount = Object.keys(incoming).length;
  const skipped = Object.keys(parsed).length - incomingCount;

  if (!incomingCount) {
    flash("読み込める記録がありませんでした。", true);
    importInput.value = "";
    return;
  }

  const overlap = Object.keys(incoming).filter((d) => entries[d]).length;
  const msg =
    `${incomingCount}件を読み込みます。\n` +
    (overlap ? `うち${overlap}件は同じ日付の既存データを上書きします。\n` : "") +
    (skipped ? `${skipped}件は形式が不正なため取り込めません。\n` : "") +
    `よろしいですか?`;
  if (!confirm(msg)) {
    importInput.value = "";
    return;
  }

  const backup = { ...entries };
  entries = { ...entries, ...incoming };    // マージ。同じ日付は incoming が勝つ
  if (!persistEntries()) {
    entries = backup;
    flashSaveError();
    importInput.value = "";
    return;
  }

  renderList();
  if (entries[dateInput.value]) fillForm(dateInput.value);
  else resetForm(true);

  flash(
    `${incomingCount}件を読み込みました。` + (skipped ? ` (${skipped}件は取り込めませんでした)` : "")
  );
  importInput.value = "";   // 同じファイルをもう一度選べるようにする
});
```

### ポイント

#### `normalizeStore` を必ず通す

これが最重要です。JSON ファイルはユーザーが手で編集できますし、
悪意ある人が変なファイルを渡すこともありえます。
**`entries` に入るデータは、必ず境界で検証されたものだけ** という原則を守ります (第11章)。

#### `await` と `async`

```js
importInput.addEventListener("change", async (ev) => {
  const text = await file.text();
```

`file.text()` はファイルの読み込みが終わるまで時間がかかるので、
**`Promise` (約束手形)** を返します。`await` を付けると「結果が出るまで待つ」動きになり、
`await` を使う関数には `async` を付ける必要があります。

この教材では非同期処理を扱っていませんが、
**`fetch` で通信するときなど、実務では必ず出てきます。** 次に学ぶべきテーマです。

#### `importInput.value = ""` を最後に置く理由

ファイル入力は「同じファイルを選び直しても `change` が発火しない」という仕様です。
値をクリアしておくと、同じファイルをもう一度読み込めます。地味ですがハマるポイントです。

#### マージ vs 全置換

```js
entries = { ...entries, ...incoming };   // マージ (後のほうが優先)
entries = incoming;                       // 全置換
```

どちらが良いかは用途次第です。「端末を移す」用途なら全置換、
「複数端末の記録を合わせる」用途ならマージが自然です。
**どちらにせよ `confirm` で何が起きるか伝える** ことが大切です。

## 問10. コードを分割する

### 選択肢A: ES Modules (きれいだが制約あり)

```html
<script type="module" src="app.js"></script>
```

```js
// constants.js
export const STORAGE_KEY = "taichou-kiroku:v1";
export const OPTIONS = { ... };
export const SCORE_FIELDS = [...];
```

```js
// app.js
import { STORAGE_KEY, OPTIONS, SCORE_FIELDS } from "./constants.js";
```

**この方法の致命的な問題**: `file://` で開くと CORS ポリシーによりブロックされ、動きません。

```
Access to script at 'file:///.../constants.js' from origin 'null' has been blocked by CORS policy
```

ローカルサーバーが必要になります。

```
python3 -m http.server 8000
```

README に書かれている「`index.html` をブラウザで開くだけで動きます (サーバー不要)」が
**成立しなくなります**。これは大きな後退です。

### 選択肢B: 名前空間オブジェクト (`file://` でも動く)

```js
// constants.js
(function (root) {
  "use strict";
  root.TaichouApp = root.TaichouApp || {};
  root.TaichouApp.constants = {
    STORAGE_KEY: "taichou-kiroku:v1",
    MAX_ENTRIES: 5000,
    MEMO_MAX: 500,
    OPTIONS: { ... },
    SCORE_FIELDS: [...],
  };
})(window);
```

```js
// utils.js
(function (root) {
  "use strict";
  const { OPTIONS } = root.TaichouApp.constants;

  function todayString() { ... }
  function addDays(iso, delta) { ... }
  function labelOf(field, value) { ... }

  root.TaichouApp.utils = { todayString, addDays, labelOf };
})(window);
```

```html
<script src="constants.js"></script>
<script src="utils.js"></script>
<script src="storage.js"></script>
<script src="xlsx.js"></script>
<script src="app.js"></script>
```

`xlsx.js` が既にこのパターンなので、**アプリ全体で書き方が統一されます** (第12章)。

**この方法の弱点**: 読み込み順を間違えると動きません。
`<script>` の順序が依存関係そのものになるため、ファイルが増えると管理が難しくなります。

### 選択肢C: 分割しない

**これも十分にありえる正解です。** 理由を挙げます。

1. **830行は「大きすぎる」サイズではありません。** 数千行を超えたら考えるべきですが、
   この程度なら1つのファイルとして十分に把握できる範囲です
2. **このアプリの最大の価値は「ダブルクリックで動く」ことです。**
   ES Modules はそれを壊します
3. **分割には必ずコストがあります。** ファイル間の依存関係、読み込み順、
   「この関数はどこにある？」という探索の手間
4. **`app.js` は既に論理的に整理されています。** 定数 → ユーティリティ → データ操作 →
   描画 → イベント登録 → 初期化、という順に並んでいて、読む順序が自然です

### 実務ではどうするか

実務では、ビルドツール (Vite、webpack など) を使います。
開発中は ES Modules で書き、ビルドすると1つのファイルにまとめられるので、
**両方の利点が得られます**。

```
開発: src/constants.js, src/utils.js, ... (import/export で書く)
  ↓ ビルド
配布: dist/app.js (1ファイルにまとまっている)
```

ただしそのためには Node.js の環境構築が必要で、
「HTMLをダブルクリックするだけ」という手軽さは失われます。

### 結論

**トレードオフを理解して、状況に応じて選ぶ。** これが正解です。

この教材のアプリのように「小規模・環境構築なし・1人で作る」なら、分割しないのが合理的です。
「大規模・チーム開発・長期メンテナンス」なら、ビルドツールを導入して分割すべきです。

**「常にこうすべき」という答えはありません。** 状況を読んで判断するのがエンジニアの仕事です。

### D. データの暗号化

`crypto.subtle` API を使います。ただし、いくつもの難しい問題があります。

- **鍵をどこに置くか**。localStorage に置いたら暗号化の意味がありません
- パスワードから鍵を導出する (PBKDF2)。反復回数の設定が必要です
- パスワードを忘れたらデータは永久に失われます
- 非同期処理 (`await`) が必須です

**「暗号は自分で設計しない」** が鉄則です。標準の API を、定石どおりに使ってください。
このアプリの用途 (自分の端末の自分の記録) なら、
**そもそも暗号化が必要か** を考えるのが先かもしれません。

### E. PWA 化

`manifest.json` と Service Worker が必要です。

**Service Worker は HTTPS またはlocalhost でしか動きません。**
`file://` では動かないので、この場合はホスティング (GitHub Pages など) が前提になります。

## 最後に

ここまでお疲れさまでした。

この教材で読んできた `app.js` は、830行ほどの小さなプログラムです。
けれども、その中には

- データ構造の設計
- 入力の検証
- エラーへの備え
- アクセシビリティ
- セキュリティ (XSS 対策)
- ユーザー体験への配慮

といった、**規模が大きくなっても変わらない考え方** が詰まっていました。

次に学ぶとよいテーマを挙げておきます。

| テーマ | なぜ必要か |
| --- | --- |
| **非同期処理** (`Promise` / `async` / `await`) | サーバーと通信するアプリには必須 |
| **`fetch` と API** | データをサーバーから取ってくる |
| **ビルドツール** (Vite) | ファイル分割と最新の文法を実用にする |
| **フレームワーク** (React / Vue / Svelte) | 画面の更新を宣言的に書く |
| **TypeScript** | 型でバグを未然に防ぐ |
| **テスト** (Vitest / Playwright) | 変更しても壊れていないことを確かめる |

ただし、どれを学ぶにしても土台は同じです。
**このアプリで見た原則は、どんなフレームワークを使っても変わりません。**

良いコードを書けるようになる一番の方法は、**良いコードをたくさん読むこと** です。
GitHub で気になるプロジェクトを開いて、この教材でやったように読んでみてください。
きっと、以前より読めるようになっているはずです。
