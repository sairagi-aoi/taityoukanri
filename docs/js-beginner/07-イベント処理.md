# 第7章 イベント処理 ― ユーザーの操作に反応する

## この章のゴール

- `addEventListener` でイベントを登録できる
- `submit` と `preventDefault()` の関係を説明できる
- **イベント委譲** の仕組みと、それが必要な理由が分かる
- `setTimeout` による時間差の処理が書ける

---

## 7-1. イベントとは

ユーザーがボタンを押す、入力する、日付を変える。こうした **出来事 (イベント)** に対して
「起きたらこれを実行して」と予約しておくのが、イベント処理です。

```js
要素.addEventListener("イベント名", 実行したい関数);
```

`app.js` の実例です。

```js
$("export-btn").addEventListener("click", exportExcel);
```

「`export-btn` がクリックされたら `exportExcel` を実行して」という予約です。
第4章で触れたとおり、**`exportExcel()` ではなく `exportExcel` を渡します**。
`()` を付けると今すぐ実行されてしまいます。

### 主なイベント

このアプリで使われているイベントです。

| イベント名 | いつ起きるか | 使われている場所 |
| --- | --- | --- |
| `click` | クリックされたとき | ボタン各種、一覧の編集・削除 |
| `submit` | フォームが送信されるとき | 記録の保存 |
| `change` | 選択や入力が確定したとき | プルダウン、日付入力、月フィルタ |
| `input` | 入力されるたび (1文字ごと) | 睡眠時間の入力 |

`change` と `input` の違いは覚えておくと便利です。

- `input` … 1文字打つたびに発火する。リアルタイムに反応したいとき
- `change` … 入力欄から離れたとき・選択が確定したときに発火する

`app.js` では睡眠時間に `input` を使っています。

```js
sleepHoursInput.addEventListener("input", () => {
  setFieldInvalid(sleepHoursInput, false);   // 打ち始めたら赤枠を消す
});
```

エラーで赤くなった枠が、**直し始めた瞬間に消える**。細かいですが、良い体験です。

## 7-2. `submit` と `preventDefault`

フォームの保存処理は、このアプリの中心です。

```js
form.addEventListener("submit", (ev) => {
  ev.preventDefault();          // ← 非常に重要
  const entry = validate();
  if (!entry) return;
  // ... 保存処理
});
```

### `ev` (イベントオブジェクト) とは

イベントが起きると、ブラウザが「何が起きたか」の情報を詰めたオブジェクトを渡してくれます。
それが第1引数の `ev` です (`e` や `event` という名前もよく使われます)。

```js
ev.target            // イベントが起きた要素
ev.preventDefault()  // ブラウザの既定の動作をやめさせる
```

### なぜ `preventDefault()` が必要なのか

HTML の `<form>` は本来、**送信するとページごとサーバーに移動する** ものです。
サーバーがない (このアプリは `index.html` を直接開いているだけ) ので、
何もしないとページがリロードされ、入力が消えてしまいます。

`ev.preventDefault()` は **「ブラウザの標準の動作を止めて」** という命令です。
これで「ページ遷移せず、JavaScript で処理する」形になります。

> **実験**: `ev.preventDefault();` の行をコメントアウトして保存し、
> フォームを送信してみてください。画面が一瞬でリセットされます。
> 確認したら必ず元に戻してください。

### なぜ `click` ではなく `submit` なのか

`save-btn` の `click` を拾ってもよさそうですが、`submit` のほうが優れています。

- 入力欄で **Enter キーを押しても** 送信される (キーボードだけで操作できる)
- ボタン以外の送信手段にも自動的に対応できる

`index.html` の `<button type="submit">` と `<form>` が組み合わさることで、
これが自動的に成立しています。**HTML の標準的な仕組みに乗ると、無料で機能が手に入る** 例です。

### 保存処理の全体

```js
form.addEventListener("submit", (ev) => {
  ev.preventDefault();
  const entry = validate();                  // ① 検査。ダメなら null
  if (!entry) return;                        // ② ダメなら何もしないで終了
  const existed = Boolean(entries[entry.date]);
  const prev = existed ? { ...entries[entry.date] } : null;  // ③ バックアップ
  entries[entry.date] = entry;               // ④ メモリ上のデータを更新
  if (!persistEntries()) {                   // ⑤ localStorage に保存
    if (prev) entries[entry.date] = prev;    //    失敗したら元に戻す
    else delete entries[entry.date];
    showError("保存に失敗しました。ブラウザの保存領域が使えない可能性があります。");
    return;
  }
  renderList();                              // ⑥ 画面を描き直す
  setFormBaseline();
  flash(existed ? "... 上書きしました。" : "... 保存しました。");   // ⑦ 通知を出す
});
```

「検査 → バックアップ → 更新 → 保存 → 失敗なら巻き戻し → 描画 → 通知」という
きれいな流れになっています。**失敗したときに元に戻す** 処理が入っているのが実務的です。

## 7-3. イベント委譲 ― 動的に作った要素のクリックを拾う

ここがこの章の核心です。

一覧の各行には「編集」「削除」のボタンがあります。記録が20件あればボタンは40個。
しかもこれらは `renderList()` が呼ばれるたびに **作り直されます**。

素直に書くとこうなります。

```js
// 悪い例
const editBtn = document.createElement("button");
editBtn.addEventListener("click", () => fillForm(date));   // 1個ずつ登録
```

これには2つの問題があります。

1. ボタンが増えるほどイベントリスナーが増える (40件なら40個)
2. `renderList()` のたびに全部作り直すので、**毎回40個登録し直し** になる

`app.js` はまったく違うアプローチを取っています。

```js
tbody.addEventListener("click", (ev) => {
  const btn = ev.target.closest("button[data-action]");
  if (!btn) return;
  const date = btn.dataset.date;
  if (!DATE_RE.test(date)) return;

  if (btn.dataset.action === "edit") {
    if (!confirmDiscard()) return;
    fillForm(date);
    form.scrollIntoView({ behavior: "smooth", block: "start" });
    $("condition").focus();
  } else if (btn.dataset.action === "delete") {
    if (!confirm(`${formatDateJa(date)} の記録を削除しますか?`)) return;
    // ... 削除処理
  }
});
```

**登録しているのは `tbody` ただ1つ。** これが **イベント委譲 (event delegation)** です。

### なぜこれで動くのか ― バブリング

クリックイベントは、クリックされた要素から **祖先に向かって伝わっていきます**。
これを **バブリング (泡が浮き上がる)** と呼びます。

```
<button> がクリックされた
  ↓ イベントが上に伝わる
<td>
  ↓
<tr>
  ↓
<tbody>  ← ここで待ち構えていれば、全部のボタンのクリックを拾える
  ↓
<table>
  ↓
<body>
```

だから `tbody` で1回だけ待ち構えれば、その中のどのボタンが押されても検知できます。

### `ev.target` と `closest` の組み合わせ

`ev.target` は **実際にクリックされた一番内側の要素** です。
ボタンの上のテキストをクリックした場合など、`ev.target` がボタン自身とは限りません。

そこで `closest` を使います。

```js
const btn = ev.target.closest("button[data-action]");
if (!btn) return;
```

「クリックされた要素から上にさかのぼって、`data-action` 属性を持つ `<button>` を探す」。
見つからなければ (ボタン以外の場所をクリックした) 何もせず終了します。

### イベント委譲の利点

| | 1個ずつ登録 | イベント委譲 |
| --- | --- | --- |
| リスナーの数 | 要素の数だけ | **1つ** |
| 再描画のたびの登録 | 必要 | **不要** |
| 後から追加した要素 | 登録し忘れると動かない | **自動的に動く** |
| メモリ | 要素数に比例 | 一定 |

`renderList()` が `tbody` の中身を丸ごと作り直しても、
**`tbody` 自身は消えないのでリスナーは生き続けます**。だから登録し直す必要がないのです。

## 7-4. データを要素に持たせる設計

イベント委譲が成り立つのは、**要素自身が「自分が何者か」を知っている** からです。

```js
// renderList の中で
editBtn.dataset.action = "edit";
editBtn.dataset.date = date;

delBtn.dataset.action = "delete";
delBtn.dataset.date = date;
```

```js
// クリックハンドラの中で
const date = btn.dataset.date;
if (btn.dataset.action === "edit") { ... }
```

これで、1つのハンドラが「どの日付の、どの操作か」を判断できます。

### 検証を忘れない

```js
const date = btn.dataset.date;
if (!DATE_RE.test(date)) return;
```

`dataset` は HTML の属性なので、開発者ツールから誰でも書き換えられます。
だから **使う前に必ず形式を検証** しています。

```js
const DATE_RE = /^\d{4}-\d{2}-\d{2}$/;
```

これは正規表現で「4桁 - 2桁 - 2桁」の形かを確かめるものです。
`test()` は当てはまれば `true` を返します。

| 正規表現の記号 | 意味 |
| --- | --- |
| `^` | 文字列の先頭 |
| `\d` | 数字1文字 |
| `{4}` | 直前のものが4回 |
| `$` | 文字列の末尾 |

`^` と `$` がないと「途中に含まれていればOK」になってしまいます。
`"abc2026-09-16xyz"` も通ってしまうわけです。**必ず両端を固定する** のがコツです。

## 7-5. `confirm` と `alert`

ブラウザ標準の確認ダイアログです。

```js
if (!confirm(`${formatDateJa(date)} の記録を削除しますか?`)) return;
```

`confirm` は「OK」なら `true`、「キャンセル」なら `false` を返します。
`!confirm(...)` で「キャンセルされたら何もせず終了」となります。

**取り消せない操作の前には必ず確認を入れる。** これは実装の話ではなく、設計の話です。
このアプリでは3か所で使われています。

```js
// ① 個別の削除
if (!confirm(`${formatDateJa(date)} の記録を削除しますか?`)) return;

// ② 全件削除 (件数を見せているのが親切)
if (!confirm(`${n}件の記録をすべて削除します。よろしいですか?`)) return;

// ③ 未保存の入力を捨てるとき
function confirmDiscard() {
  if (!isFormDirty()) return true;   // 変更がなければ聞かない
  return confirm("入力内容は保存されていません。破棄して続けますか?");
}
```

③ の気配りに注目してください。**変更がないときは聞かない** のです。
何も入力していないのに「破棄しますか？」と毎回聞かれたら、うっとうしいだけです。

「変更があったか」の判定はこうなっています。

```js
function getFormSnapshot() {
  const snap = { date: ..., sleepHours: ..., memo: ... };
  for (const field of SCORE_FIELDS) snap[field] = $(SELECT_IDS[field]).value;
  return snap;
}

function isFormDirty() {
  if (!formBaseline) return false;
  const cur = getFormSnapshot();
  return JSON.stringify(cur) !== JSON.stringify(formBaseline);
}
```

フォームの状態をオブジェクトとして取り、**`JSON.stringify` で文字列にしてから比較** しています。
オブジェクト同士を `===` で比べると「同じ住所か」の比較になってしまう (第3章) ので、
文字列に変換して中身を比べているわけです。簡単で確実な小技です。

## 7-6. `setTimeout` ― 時間差で実行する

保存すると出る「保存しました」の通知は、数秒後に自動で消えます。

```js
let flashTimer = null;
function flash(msg, isError) {
  if (!appToast) return;
  appToast.textContent = msg;
  appToast.classList.toggle("is-error", Boolean(isError));
  appToast.hidden = false;
  clearTimeout(flashTimer);              // ← 前のタイマーを取り消す
  flashTimer = setTimeout(() => {
    appToast.hidden = true;
    appToast.textContent = "";
  }, 4000);                              // 4000ミリ秒 = 4秒後
}
```

`setTimeout(関数, ミリ秒)` で「◯ミリ秒後にこの関数を実行して」と予約できます。

### `clearTimeout` が要る理由

連続で2回保存したらどうなるでしょう。

`clearTimeout` がないと:

1. 1回目の保存 → 4秒後に消すタイマーA をセット
2. 2秒後に2回目の保存 → 4秒後に消すタイマーB をセット
3. **その2秒後、タイマーA が発火して通知が消えてしまう** (2回目の通知は2秒しか出ない)

`clearTimeout(flashTimer)` で古いタイマーを取り消しておけば、
常に「最後の通知から4秒」で消えます。

**タイマーをセットするときは、古いタイマーの取り消しをセットで書く。** 定番のパターンです。

### もう1つの `setTimeout`

Excel 書き出しの最後にも出てきます。

```js
const url = URL.createObjectURL(blob);
const a = document.createElement("a");
a.href = url;
a.download = `体調記録_${todayString()}.xlsx`;
document.body.appendChild(a);
a.click();
a.remove();
setTimeout(() => URL.revokeObjectURL(url), 1000);
```

ダウンロードが始まるのを待ってから、一時的な URL を解放しています。
すぐに解放するとダウンロードが失敗する可能性があるため、1秒の猶予を置いています。
詳しくは第12章で扱います。

## 7-7. 「変更を確認してから進む」パターン

日付を変えるときの処理を読んでみましょう。

```js
dateInput.addEventListener("change", () => {
  if (!confirmDiscard()) {
    dateInput.value = lastDateValue;   // ← キャンセルされたら日付を戻す
    return;
  }
  lastDateValue = dateInput.value;
  if (entries[dateInput.value]) {
    fillForm(dateInput.value);
  } else {
    resetForm(true);
  }
});
```

ここに `lastDateValue` という変数が効いています。

`change` イベントは **日付が既に変わった後** に発火します。
ユーザーが「キャンセル」を選んでも、入力欄の表示は新しい日付のままです。
だから `lastDateValue` に直前の値を覚えておいて、**手動で戻している** のです。

`let lastDateValue = ""` が `let` である理由が、ここで分かります。

## まとめ

- `addEventListener("イベント名", 関数)` で反応を予約する。**関数は `()` を付けずに渡す**
- `submit` + `ev.preventDefault()` で、ページ遷移せずにフォームを処理する
- **イベント委譲**: 親に1つだけリスナーを付け、`ev.target.closest()` でどれが押されたかを判定する
- 動的に作り直される要素のイベントは、委譲で扱うのが定石
- `dataset` で「その要素が何者か」を持たせる。ただし **使う前に必ず検証する**
- 取り消せない操作の前には `confirm`。ただし変更がないときは聞かない
- `setTimeout` でタイマーを仕掛けたら、`clearTimeout` で古いタイマーを取り消す
